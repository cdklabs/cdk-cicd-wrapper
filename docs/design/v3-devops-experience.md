# CDK CI/CD Wrapper v3 — DevOps Experience Proposal (DRAFT for iteration)

Status: brainstorming draft — core decisions below are agreed with the maintainer; details still iterating.

## Goals

1. **Zero-touch onboarding**: an autogenerated `cdk init` app deploys single-account/single-region
   with `npm run cdk deploy` — no changes in `bin/` (or one optional line for advanced cases).
2. **Separate configuration file**: stages, accounts, regions, and CI/CD settings live in a typed
   config file (`cicd.config.ts` / `cicd_config.py`), not in the bin file, not in env vars,
   not in `package.json#config`.
3. **Engine abstraction**: CodePipeline remains the default CD engine, but the same model renders
   to a container-based flow (GitLab CI, GitHub Actions, Jenkins) where the wrapper
   generates/publishes purpose-built Docker images — the Automation Framework pattern: the image is
   a **config-agnostic, versioned payload** (CDK app code + wrapper tooling + pinned deps). Config is
   injected at deploy time → the container **synths against that config → deploys** per target.
4. **Radically fewer CodeBuild projects** (a real project hit 100+; v2 drivers: per-asset
   publishing, per-stage Pre/PostDeploy steps, self-mutation, CodeGuru, PR checks).
5. Keep v2's capabilities: multi-stage deployment, CI step customization, hooks, plugins,
   compliance bucket, VPC/proxy/private-registry support.
6. Ship as a **breaking v3 major** with a migration guide (v2 API removed, concepts mapped).

## Agreed decisions

| Topic | Decision |
|---|---|
| Config format | Typed code file (`cicd.config.ts`), discovered by convention; jsii-friendly equivalent for Python |
| Docker/artifact model | Alternative engine; CodePipeline stays the default engine |
| No-config behavior | Plain direct deploy — wrapper inert until a config file exists |
| Versioning | Breaking v3 major + migration guide |
| Deploy model | **Two CodePipeline implementations** (see below), *efficiency first*. **Default: assembly promotion (the v2 way)** — the synth/Build phase synths every stage **once**, keeps `cdk.out`, and promotes it as the pipeline artifact; deploy stages consume it and never re-synth. **Second option: per-stage synth at deploy time** — the promoted immutable unit is **code + pinned deps** (git sha / image digest) and config is injected per target at deploy time; there, CI synths **one env by default** and anything already synthed is reused. Docker mode always synths at run time (config-agnostic image). First-class multi-region, forced deployer/synthesizer roles. |
| Pipeline lifecycle | Self-updating pipeline (CodePipeline-self-mutation-like); **initialized via CLI** (`cdk-cicd deploy-ci`); cdk.json integration via feature flag/context only — **no wrapper code required in the CDK app codebase** |
| CI checks | **Default-on like v2** (validate, audit, license, security scans) — but implemented as wrapper-CLI commands run in CI, so a fresh project passes without adding npm scripts or jq surgery |
| Synthesizer | **Default: `DefaultStackSynthesizer`** with optional forced roles; `AppStagingSynthesizer` is **opt-in** (`synthesizer: 'app-staging'`) until it's stable. Either is installed by the wrapper's `cdk.json` app command / register hook — no bin change. Forced roles via `DeploymentIdentities.specifyRoles` (app-staging) or `deployRoleArn`/`cloudFormationExecutionRole` (default) |
| App injection | Wrapper owns the **`cdk.json` `app` command** (`npx cdk-cicd exec <entry>` / `node -r .../register`); no imports in the app's CDK code |
| Docker mode | **Two-repo split**: Repo 1 (CDK app) runs CI + builds/pushes a **config-agnostic** deployer image = CDK code + vendored npm deps + tooling (**not `cdk.out`**), so it runs **offline**; Repo 2 (generic, config-driven) runs the image against its own config, `cdk deploy` **synthesizing per target at run time**, then deploys to any account/region. Not a single generated pipeline file |
| Hooks | **Portable shell commands** (run by the CLI, render to any engine) + **optional typed CDK-construct hook** (Lambda/StateMachine) for CodePipeline-native needs, documented as engine-dependent |
| Artifact store | **S3 versioned bucket by default**; ECR/OCI artifact supported |
| Per-stage config | First-class **config-management layer**: load + merge + validate JSON/YAML per stage. **Generic loader + optional opinionated base schema** (accounts/regions/tags/removalPolicies/networking) users extend or ignore (see below) |
| Config authoring | **`cicd.config.ts` primary** (typed, can hold hooks/plugins); **`cicd.config.yaml` fully supported** for zero-code teams — code-only features require the TS form |

## The three user experiences

### Level 0 — plain CDK app (zero touch)

```bash
npx aws-cdk init app --language typescript
npm run cdk deploy        # deploys to current account/region. Wrapper not involved.
```

Nothing to learn. The wrapper only activates when a config file exists.

### Level 1 — add stages + CI/CD with one file

Drop a `cicd.config.ts` next to `cdk.json` (discovered by convention):

```ts
import { defineCICD, Repository } from '@cdklabs/cdk-cicd-wrapper';

export default defineCICD({
  application: 'my-app',            // replaces npm_package_config_applicationName
  qualifier: 'myapp',               // replaces CDK_QUALIFIER env var
  repository: Repository.github('my-org/my-app'),   // or .codecommit(), .s3(), .gitlab()

  stages: [
    { name: 'dev',  env: { account: '111111111111', region: 'eu-west-1' } },
    { name: 'int',  env: { account: '222222222222', region: 'eu-west-1' }, manualApproval: true },
    {
      name: 'prod',
      // multi-region: one logical stage, N regional deployments (sequential or parallel)
      env: { account: '333333333333', regions: ['eu-west-1', 'us-east-1'], regionOrder: 'sequential' },
      manualApproval: true,
      // force deployment through a controlled role (Automation Framework pattern)
      deployment: {
        deployRole: 'arn:aws:iam::333333333333:role/automation-deployer',
        cfnExecutionRole: 'arn:aws:iam::333333333333:role/automation-deployer',
      },
    },
  ],

  ci: {
    // Default-on checks (validate, audit:deps, audit:security, license, lint, test, synth).
    // Implemented by the cdk-cicd CLI inside CI — no npm scripts required in the user project.
    // Users can override/disable individual steps or add their own:
    steps: { build: 'npm run build' },
    synthStages: 'all',             // default: synth EVERY stage in CI as a validation check
                                    // (the deployed template is synthed at deploy time, not here);
                                    // or ['dev','prod'] to limit which stages CI validates
    image: 'public.ecr.aws/...',    // or Image.fromDockerfile('ci/Dockerfile')
  },
});
```

- `cdk deploy` (no args) still does the direct Level-0 deploy — the developer inner loop
  (v2 "workbench" becomes simply: direct deploy with your own credentials).
- No mandatory npm scripts, no `jq` surgery, no `package-verification.json` setup pain, no
  dotenv-cli. The compliance checks still run in CI by default — the CLI owns them.

### Level 2 — enterprise / Automation Framework mode (two-repository split)

This is the scale-out pattern, and it is **two repositories**, not one generated pipeline file:

**Repo 1 — CI / build (the CDK app repo).** Holds the CDK code. Its pipeline runs CI (lint, test,
audit, and a synth **as a validation check**) and then **builds & pushes a Docker image** whose
payload is just the **CDK app code + its npm dependencies** (installed into the image) + the wrapper
deployer tooling — **config-agnostic and hash-versioned** (git sha / image digest). Vendoring the
deps means the image runs **offline / air-gapped**: no `npm install` and no registry access at deploy
time. **`cdk.out` is never baked into the image** — no per-stage assembly is included; `cdk deploy`
synthesizes it fresh at run time against the injected config. The build ends at "image pushed"; it
deploys nothing. This is where the wrapper's `image` build + optional registry push lives.

```ts
// Repo 1: cicd.config.ts
export default defineCICD({
  application: 'my-app',
  repository: Repository.github('my-org/my-app'),
  build: BuildImage.docker({                    // produce & push the CONFIG-AGNOSTIC deployer image
    dockerfile: 'ci/Dockerfile',                // optional; a default image is provided
    registry: 'ACCT.dkr.ecr.eu-west-1.amazonaws.com/my-app-cicd',
    tag: 'git',                                 // git-sha / semver tag strategy
  }),
  // CI runs lint/test/audit + a synth-as-a-check. NOTHING is baked into the image per stage;
  // the deployed template is synthed at run time in Repo 2, against each target's config.
});
```

**Repo 2 — CD / deploy (the generic deployer).** A separate, app-agnostic repo (or the wrapper's
own runner) that **runs the pushed image** against **its own config**: for each target the container
synthesizes the app with that target's stage env + config, then deploys — to **any account/region**,
with no CDK code in this repo. One image → many CD invocations, each supplying its own config. This
is what collapses the 100+ CodeBuild footprint: targets are config rows, not pipeline resources.

```ts
// Repo 2: deploy.config.ts  (drives `cdk-cicd deploy --from-image`)
export default defineDeployment({
  image: 'ACCT.dkr.ecr.eu-west-1.amazonaws.com/my-app-cicd:1.4.2',
  targets: [
    { stage: 'dev',  env: { account: '111111111111', region: 'eu-west-1' } },
    { stage: 'prod', env: { account: '333333333333', regions: ['eu-west-1', 'us-east-1'] },
      manualApproval: true,
      deployment: { deployRole: 'arn:aws:iam::333333333333:role/automation-deployer' } },
  ],
});
```

- CD synths **in-container against the target's config** and deploys the result per target, with
  approval gates and cross-account STS role assumption per target.
- Determinism without baking: the pinned image (code + deps) plus config-supplied lookups (no
  `fromLookup` at synth) mean the same image + same config always synths the same template.
- Rollback = point `image:` at the previous version tag and redeploy with its config. Optional
  `cdk diff` drift gate before deploy.
- The CD side is engine-neutral by construction: the same image + `deploy.config.ts` runs under
  GitLab, Jenkins, GitHub Actions, or a plain `docker run`.

## Deploy model: two implementations, promotion by default

> **Amended 2026-08-20 (maintainer).** This section originally declared per-stage deploy-time synth the
> single decided model. It is now the **second** of two CodePipeline implementations; the **default** is
> assembly promotion. Guiding principle: **efficiency first**. See `task.md` D-deploy for the decision
> record and `m4-assembly-promotion` / `m4-synth-efficiency` for the work.
>
> **1. Default — assembly promotion (the v2 CodePipeline way).** The synth/Build phase synths every
> stage **once** and **keeps `cdk.out`**; that assembly is promoted as the pipeline's output artifact and
> each deploy stage **consumes** it, performing no synth of its own. One synth per pipeline run.
>
> **2. Second option — per-stage synth at deploy time** (described in the rest of this section, and what
> M4 shipped and proved in `m4-verify`). Two efficiency rules apply to it: the Build phase synths **one
> env by default** rather than `--all` (the others synth when their own stage runs), and any assembly
> Build already produced is **reused rather than re-synthed** — `cdk-cicd deploy --from-assembly`
> deploys a promoted `cdk.out/<stage>/<region>` instead of synthesizing again.
>
> Orthogonal to both (D-deploy-wait): a deploy action must not bill CodeBuild compute while it merely
> waits on CloudFormation — a **stateful Lambda** observes deployment state and completes the action.

The bin file stays exactly as `cdk init` generated it. The **promoted immutable unit is the code +
pinned deps** (a git sha, or a Docker image digest) — *not* a baked cloud-assembly. At **deploy
time**, for each target, the wrapper CLI synths the app with that target's stage-scoped environment
(`CDK_DEFAULT_ACCOUNT`/`CDK_DEFAULT_REGION` **and** `CDK_DEPLOY_ACCOUNT`/`CDK_DEPLOY_REGION` set from
the stage's `env`, plus `CDK_STAGE=<name>` and the per-stage config) into
`cdk.out/<stage>/<region>/`, then deploys the freshly-synthed assembly via `cdk-assets publish` +
CloudFormation (or `cdk deploy --app <assembly>`). Synth runs **at deploy, against the injected
config** — the same mechanism for every engine:

- **CodePipeline engine** (the CDK-Pipelines replacement): ONE synth CodeBuild project + ONE deploy
  action per stage; synth runs in the pipeline against each stage's config at execution time —
  directly attacks the 100+ CodeBuild problem (no per-asset projects, no per-stage Pre/PostDeploy
  projects; hooks run inside the deploy step or as lightweight actions).
- **Container engines**: the same `cdk-cicd` commands run inside the pushed image; config is injected
  at run time (Repo 2), so one config-agnostic image deploys to any target. The image carries the CDK
  code + npm deps (not `cdk.out`), so `cdk deploy` synthesizes and deploys **offline** — no registry
  or `npm install` at deploy time.

**Determinism without baking.** Because v3 replaces `*.fromLookup` with config-supplied attributes
(the app-config layer) and the sha/image pins code + deps, deploy-time synth is reproducible — the
same `(code, deps, config)` always yields the same template. Rollback = redeploy a previous sha /
image tag with its config.

### CI synth scope (validation only)

> **Amended:** true only for implementation 2. In the **default** (promotion) implementation CI's synth
> *is* the deployed artifact — it is kept and promoted, not discarded. Also note `ci.synthStages` is
> currently **declared but read by nothing** (finding `qa-ci-synthstages-declared-but-inert`), so the
> narrowing described below does not yet work; `m4-synth-efficiency` wires it and flips the default to
> one env.

Synth at CI time is a **validation check** — it proves every stage's config synthesizes cleanly and
fails the build fast if one doesn't. It does **not** produce the deployed artifact (that is synthed
at deploy time, above). Default: CI validates **all** configured stages; `ci.synthStages` narrows
this when synth cost matters. For a Docker build the deployed template is always synthed at run time
in Repo 2, so `synthStages` there is purely a CI gate, not an artifact control — and typically unset.

### Multi-region

A stage may declare `regions: [...]`. The wrapper produces one assembly per (stage, region) and
deploys them in configured order (`sequential` default; `parallel` opt-in), setting
`CDK_DEFAULT_REGION`/`CDK_DEPLOY_REGION` per region. Both stock app shapes are multi-region-capable
with zero code change, by different routes: an app using
`env: { account: process.env.CDK_DEFAULT_ACCOUNT, region: process.env.CDK_DEFAULT_REGION }` pins each
assembly to the injected region **at synth**; a fully env-agnostic app (no `env`) synths
region-agnostic templates (`AWS::Region` pseudo-param) that deploy to whatever region the deploy
targets. Global/one-region-only stacks can be pinned via per-stack config (`onlyRegions` /
`excludeRegions` matching by stack name pattern).

### Forced deployer / synthesizer roles

Config `stages[].deployment` forces controlled roles, equivalent to:

```ts
new DefaultStackSynthesizer({
  deployRoleArn: process.env.AUTOMATION_ROLE_ARN,
  cloudFormationExecutionRole: process.env.AUTOMATION_ROLE_ARN,
});
```

Mechanics (bin stays untouched):
- The CLI exports the configured role ARNs as env vars (`CDK_CICD_DEPLOY_ROLE_ARN`, …) during synth
  and passes them at deploy time (`--role-arn`, cdk-assets role overrides).
- If full synthesizer control is required (asset-publishing roles are baked into the asset manifest
  at synth), the wrapper offers an optional one-liner for the bin file:
  `new App({ defaultStackSynthesizer: CicdSynthesizer.fromConfig() })` — the documented escape
  hatch for strict enterprise setups. (OPEN: evaluate injecting synthesizer settings purely via
  context so even this line is unnecessary.)

## App injection & synthesizer (research-backed)

**The seam: `cdk.json`'s `app` command.** The CDK CLI runs whatever the `app` key says to produce
the cloud assembly. The wrapper owns this line — written by `cdk-cicd configure`/`deploy-ci`, never
by the user editing `bin/`:

```json
{ "app": "npx cdk-cicd exec bin/app.js" }
```

`cdk-cicd exec` is a thin launcher that:
1. loads `cicd.config.ts` + the per-stage config (below) and exports stage env — the stage's
   `env.account`/`env.region` populate **both** `CDK_DEFAULT_ACCOUNT`/`CDK_DEFAULT_REGION` **and**
   `CDK_DEPLOY_ACCOUNT`/`CDK_DEPLOY_REGION`, plus `CDK_STAGE`. This is what lets the **untouched
   `cdk init` app** resolve the correct target with its stock line
   `env: { account: process.env.CDK_DEFAULT_ACCOUNT, region: process.env.CDK_DEFAULT_REGION }` —
   the user writes **no** `cfg.aws.*` reference and no per-stage `env` of their own.
   (Caveat: this requires the app to *use* that stock env line. An app with `env` omitted entirely
   is env-agnostic and synths to `unknown-account/unknown-region` regardless — see the drift check.)
2. merges wrapper context into `CDK_CONTEXT_JSON` (supported CLI mechanism — the app reads it via
   `node.tryGetContext` with no code change);
3. runs the user entry with a **register hook** (`node -r @cdklabs/cdk-cicd-wrapper/register`) that
   subclasses `App` to (a) install the default synthesizer, (b) apply plugins/Aspects
   (cdk-nag, encryption defaults) across the tree, (c) apply stack tags.
   Python gets an equivalent import hook; the documented one-liner
   `CdkCicd.attach(app)` remains a fallback for bundlers/runtimes where the hook can't load.

#### Seam mechanics — spiked and verified (aws-cdk-lib 2.195.0, node 24)

A throwaway prototype (`node -r register.js` + an untouched `cdk init`-shaped app) confirmed the
approach and corrected three assumptions:

1. **The leaf module is not importable by subpath.** `require('aws-cdk-lib/core/lib/app')` fails with
   `ERR_PACKAGE_PATH_NOT_EXPORTED` — `aws-cdk-lib`'s `exports` map does not publish it. The hook must
   resolve the file directly, which bypasses the exports map:
   ```js
   const cdkRoot = path.dirname(require.resolve('aws-cdk-lib/package.json'));
   const appModule = require(path.join(cdkRoot, 'core/lib/app.js'));
   ```
   This is the load-bearing fragility of the preload approach: it depends on `aws-cdk-lib`'s internal
   file layout, so it needs a clear failure mode and a version check, not just a try/catch.
2. **Patching the leaf propagates everywhere.** `appModule.App` is a writable data property, and both
   `aws-cdk-lib` and `aws-cdk-lib/core` expose `App` as a *lazy accessor* that re-reads the leaf on
   every access — so assigning `appModule.App = WrappedApp` is observed through every import path
   (verified: `require('aws-cdk-lib').App === WrappedApp`). One patch point, not N. The top-level
   accessors are also `configurable: true`, so `Object.defineProperty` is a viable second seam if the
   internal path ever moves.
3. **Both stock entry shapes work.** Verified for a plain `bin/app.js` and for a TypeScript
   `bin/app.ts` under `node -r <register> -r ts-node/register bin/app.ts` (what `cdk init --language
   typescript` produces). In both cases, with the hook: the App is the subclass, injected context is
   readable via `tryGetContext`, Aspects visit the whole tree, tags reach the synthesized template,
   and the stage's `CDK_DEFAULT_ACCOUNT`/`_REGION` land on the stack — **with zero edits to `bin/`**.
   Without the hook the wrapper is completely inert (plain `App`, no context, no Aspects, no tags),
   which is the Level-0 guarantee.

**Bundled entries fail silently — this is why `attach()` is mandatory, not a nicety.** Verified against
a real 43 MB esbuild bundle: esbuild inlines `aws-cdk-lib`, so the bundle constructs its own inlined
`App` class and never consults the module registry. The hook loads, patches nothing observable, and
the app synthesizes **successfully with no synthesizer, no tags and no Aspects** — a silently
non-compliant deploy, which is worse than a crash. Native ESM entries and a vendored `aws-cdk-lib`
copy have the same shape.

Detection (spiked, works): the hook counts how many Apps came through its constructor and asserts on
`process.on('exit')` — *hook loaded + zero constructions + success exit* means injection was bypassed.
It then fails the synth non-zero with an actionable message pointing at `CdkCicd.attach(app)`. Verified
silent on a normal app and erroring on the bundle. This makes the failure loud at synth time rather
than at audit time.

**Synthesizer — `DefaultStackSynthesizer` is the v3 default; `AppStagingSynthesizer` is opt-in.**
Because app-staging is still alpha (API churn, 20-ECR-image cap), v3 defaults to
`DefaultStackSynthesizer` (with optional forced `deployRoleArn`/`cloudFormationExecutionRole`).
Teams opt in with `synthesizer: 'app-staging'`. Both sit behind the wrapper's own synthesizer
interface so the default can flip later without breaking users. Research findings on app-staging
that justify offering it (and eventually promoting it):
- It **does not support CDK Pipelines — requires `cdk deploy`**. v3 synths per stage at deploy time
  and deploys with `cdk deploy`, so this aligns instead of conflicts (a reason *not* to keep CDK
  Pipelines).
- Forced deployer/CFN-execution roles are first-class via
  `DeploymentIdentities.specifyRoles({ deploymentRole, cloudFormationExecutionRole, lookupRole })`
  — cleaner and more supported than hand-writing `DefaultStackSynthesizer({ deployRoleArn, ... })`.
  `stages[].deployment` in the config maps straight onto this.
- Per-app/per-env staging + **roles-only, single-region bootstrap** + per-image ECR repos with
  lifecycle rules → directly reduces the bootstrap/asset sprawl behind the 100+ problem.
- Constraints to design around: `appId` required (use `application`), `stagingBucketEncryption`
  required, **max 20 independent ECR images per app**, still alpha (pin + wrap so we can swap).

The register hook sets `new App({ defaultStackSynthesizer: <resolved from config> })` — so even the
synthesizer choice needs no bin change.

## Application configuration management (per-environment, first-class feature)

> This is about the **application's own CDK-code configuration** — the per-environment values the
> stacks consume (VPC ids, hosted zones, ACM ARNs, feature toggles, tags, removal policies…). It is
> **not** the pipeline/CICD config from `cicd.config.ts`. The two are independent.

Every application has settings that differ per environment. v3 ships a **config-management layer**
that, for whichever stage is being synthesized, automatically loads the matching config file and
makes it available to the CDK code in `bin/` and the stacks:

- `cdk deploy` (local inner loop, Level 0) → loads **`config/local.json`**.
- Pipeline/CD synth for a stage → loads **`config/<stage>.json`** (e.g. `config/dev.json`,
  `config/prod.json`), because the wrapper sets `CDK_STAGE` when it invokes the app.
- `.yaml`/`.yml` accepted alongside `.json`.

The bin/stack code reads it through a typed accessor — this is the one place app code intentionally
uses a wrapper API, and it stays tiny:

```ts
// bin/app.ts — the app OWNS how it uses config; the wrapper only resolves & injects it.
import { CdkCicd } from '@cdklabs/cdk-cicd-wrapper';
const app = new App();
const cfg = CdkCicd.config<EnvConfig>();      // resolved config for the active stage / local
new MyStack(app, 'my-app', {
  // env is OPTIONAL: `exec` already exports the stage's account/region into
  // CDK_DEFAULT_ACCOUNT/REGION (+ CDK_DEPLOY_ACCOUNT/REGION), so the stock cdk init line
  //   env: { account: process.env.CDK_DEFAULT_ACCOUNT, region: process.env.CDK_DEFAULT_REGION }
  // already targets the right stage. Only read cfg.aws.* to override.
  vpcId: cfg.networking.vpcId,                 // per-env values still come from config
});
```

(For a zero-touch app that doesn't need per-env values, none of this is required. It also stays
readable from context — `node.tryGetContext('cicd:config')` — so even the accessor import is
optional. And because the stage's account/region are injected via `CDK_DEFAULT_*`/`CDK_DEPLOY_*`,
the app never needs to wire `env` from `cfg` just to hit the right account/region.)

Design (kept CDK-free and dependency-injectable, mirroring the maintainer's proven
`ConfigLoader`/`EnvConfig` pattern):
- **Resolution**: `CONFIG_FILE` env override → else `config/<stage>.(json|yaml)` derived from
  `CDK_STAGE` → else `config/local.*` for plain `cdk deploy`. Total function, never throws.
- **Layering**: `defaults` < file (deep-merge, last-wins) → `applyDerivedDefaults` (region
  inheritance, account-derived names) → structural validation.
- **Validation with typed error kinds**: `MISSING_FILE | PARSE_ERROR | MISSING_KEY |
  MISSING_ATTRIBUTE`, addressed by dot-path required-field tables, plus conditional groups (a group
  becomes required only when its parent is present, e.g. the Frankfurt-VPC example). A `ConfigError`
  is thrown uncaught at the entry point so `cdk synth` exits non-zero and emits no templates.
- **Generic loader + optional base schema**: the wrapper provides the loader, merge,
  derived-defaults hook, and validation primitives generic over a user `<T>` (the app defines its
  own `EnvConfig` shape and required-field tables), PLUS a small opinionated base schema —
  `aws.accountId`/`aws.region`, `tags`, `removalPolicies`, `application` — that apps extend or
  ignore. **Networking is deliberately NOT in the base schema** (too app-specific; apps model their
  own VPC/subnet/hosted-zone shape). Optional JSON Schema validation so YAML/JSON authored by
  non-TS users gets the same guarantees.

Reused primitives (to port, not reinvent): `ConfigLoader.resolvePath/load/validate`, `deepMerge`,
`applyDerivedDefaults`, `getDefaultConfig`, `DeepPartial`, `ConfigError`, dot-path `getByPath`,
required-field tables with conditional groups.

## Pipeline lifecycle (decided)

- **Init**: `npx cdk-cicd deploy-ci` — reads `cicd.config.ts`, deploys the pipeline + repository +
  support stacks (encryption, compliance bucket, SSM params) to the hub/RES account. For container
  engines it builds/pushes the Docker images and emits the engine definition files instead.
- **Self-update**: the running pipeline re-synths its own definition from `cicd.config.ts` on each
  execution and applies changes (CodePipeline self-mutation equivalent; for container engines the
  generated definition is re-emitted and committed/applied).
- **cdk.json**: integration is limited to context/feature-flag entries written by `deploy-ci`
  (e.g. qualifier, stage defaults) — no wrapper imports in the app's CDK code.

| `defineStages` + `ACCOUNT_*` env vars | Replaced by `stages:` in config file (env-var interpolation supported for secrets/accounts) |

| GitHubPipelinePlugin (buildspec reverse-engineering) | Replaced by first-class engine renderer |

## Resolved via research

- **Injection seam**: `cdk.json` `app` command + `node -r register` hook + `CDK_CONTEXT_JSON`.
  No bin edits; matches "integrate into cdk.json as a feature flag, no code in the CDK codebase".
- **Synthesizer/roles without bin change**: register hook installs `AppStagingSynthesizer`
  (or `DefaultStackSynthesizer`) with roles from config; `DeploymentIdentities.specifyRoles`.
- **Artifact store**: S3 versioned default; ECR/OCI supported.
- **Plugins/Aspects under CLI-driven synth**: applied by the register hook wrapping `app.synth()`.

## Resolved via iteration

- Config authoring: `cicd.config.ts` primary, `cicd.config.yaml` fully supported.
- App config-management shape: generic loader + optional opinionated base schema.
- Synthesizer default: `DefaultStackSynthesizer` (forced roles optional); app-staging opt-in.
- Hooks: portable shell commands + optional typed CDK-construct hook.
- Docker mode: two-repository split (build/push image ↔ generic config-driven deployer);
  the CD side uses a **separate `defineDeployment({ image, targets })`** entry point.
- RES/hub stage: **implicit and engine-dependent** — auto-added only for the CodePipeline engine.
  Wrapper support resources (encryption key, logging/compliance bucket, SSM params) are deployed
  **on demand**: only the pieces the app actually references via DI get provisioned.
- App config-management is about the **application's** per-env config (`config/<stage>.json`,
  `config/local.json`), auto-loaded per active stage and read by the bin/stack code.

## Implementation plan

### Guiding constraints

- **Don't kill v2.** Ship v3 in the **same monorepo** as **new modules alongside** the v2 code
  (jsii-published, projen-managed). v2 (`PipelineBlueprint`) keeps building and is only removed at
  the v3.0 major with a migration guide + codemod assist. Every step below is additive until the
  final flip.
- **Reuse, don't reinvent.** The engine-agnostic v2 assets carry over: the `ResourceContext`/
  `IResourceProvider` DI concept, the stage/`DeploymentDefinition` model, phase-command model, and
  the Aspect-based plugins. The maintainer's `ConfigLoader`/`EnvConfig` primitives are ported for
  the app-config layer.

### Package / module layout (in `packages/@cdklabs/`)

| Package / module | Contents |
|---|---|
| `cdk-cicd-wrapper/src/v3/config` | `defineCICD`, `defineDeployment`, config types, TS+YAML loader, resolution |
| `cdk-cicd-wrapper/src/v3/appconfig` | Ported `ConfigLoader`/`deepMerge`/`applyDerivedDefaults`/`ConfigError` + base `EnvConfig` schema (no networking); `CdkCicd.config<T>()` accessor + `cicd:config` context |
| `cdk-cicd-wrapper/src/v3/runtime` | `register` hook (wraps `App`/`app.synth`), synthesizer install, plugin/Aspect application, tags, stage-env injection |
| `cdk-cicd-wrapper/src/v3/engine` | `IEngine` interface + `CodePipelineEngine` (first), `GitHubActionsEngine`, `ContainerEngine` (later) |
| `cdk-cicd-wrapper/src/v3/support` | Lazy support providers reshaped from v2 (encryption, logging/compliance bucket, SSM, VPC, proxy) behind a de-singletoned `ResourceContext` |
| `cdk-cicd-wrapper-cli/src/cmds/v3` | `exec`, `synth`, `publish`, `deploy`, `deploy-ci`, `diff`, `configure` (absorbs existing `validate`/`audit`/`license`/`security`) |

### Milestones (each independently shippable, additive)

1. **App-config layer** (lowest risk, immediately useful, standalone). Port `ConfigLoader` &
   friends; add base `EnvConfig` (no networking); `CdkCicd.config<T>()` + context; stage/`local`
   resolution driven by `CDK_STAGE`. Unit tests mirror the reference (`MISSING_FILE|PARSE_ERROR|
   MISSING_KEY|MISSING_ATTRIBUTE`, conditional groups).
2. **Runtime injection + `cdk-cicd exec`**. `cdk.json` `app` command; register hook installs
   synthesizer (default `DefaultStackSynthesizer`, forced roles from config; `AppStagingSynthesizer`
   opt-in), applies plugins/Aspects, sets stage env + `CDK_CONTEXT_JSON`. Verifies Level 0
   zero-touch deploy still works.
3. **`defineCICD` + resolution + deploy-time synth**. Config types, defaults expansion (the "resolved
   config"), per-(stage×region) synth into `cdk.out/<stage>/<region>` run at deploy time against the
   target config, `cdk-cicd synth --all` for CI validation.
4. **CodePipeline engine (default)**. `IEngine` + `CodePipelineEngine`: one synth project + one
   deploy action per stage (assets via `cdk-assets`), lazy support resources, manual-approval
   gates, `cdk-cicd deploy-ci` to provision/self-update. This is the v2 feature-parity bar.
5. **Migration**: `MIGRATION.md` v2→v3 chapter + mapping table + a `cdk-cicd migrate` codemod that
   rewrites a v2 `PipelineBlueprint.builder()...synth(app)` into `cicd.config.ts` + `cdk.json` app
   command where mechanical.
6. **Container two-repo mode**: `BuildImage.docker` (Repo 1 build/push), `defineDeployment`
   (`cdk-cicd deploy --from-image`, Repo 2), S3 artifact store default + ECR/OCI support.
7. **GitHub Actions engine** (reworked from the v2 `GitHubPipelinePlugin`, no buildspec
   reverse-engineering — renders from the model directly).
8. **Deprecate/remove v2** at the v3.0 major once parity + migration are proven.

### v2 → v3 mapping (feeds MIGRATION.md)

| v2 | v3 |
|---|---|
| `PipelineBlueprint.builder().defineStages(...).addStack(...).synth(app)` | `defineCICD({ stages, ... })` in `cicd.config.ts`; stacks stay in `bin/` |
| `ACCOUNT_<STAGE>` / `CDK_QUALIFIER` / `npm_package_config_*` env | fields in `cicd.config.ts` (env interpolation still allowed) |
| `RepositorySource.codecommit()/github()/s3()` | `Repository.codecommit()/github()/codestarConnection()/s3()` |
| `IResourceProvider` + `ResourceContext.instance()` singleton | same DI concept, **de-singletoned**, typed lookups |
| `definePhase`/`PhaseCommand` | `ci.steps` command map |
| Plugins (Aspect-based) | unchanged; applied by the runtime hook |
| `BaseStackProvider` pre/post hooks (`pipelines.Step`) | portable shell `hooks` + optional CDK-construct hook |
| `workbench(...)` | Level-0 direct `cdk deploy` |
| `GitHubPipelinePlugin` | first-class `Engine.githubActions()` |

### Verification (end-to-end)

- **Build**: `cd packages/@cdklabs/cdk-cicd-wrapper && npx projen build` (jsii compile + tests) after
  each milestone; save log to a temp file and tail it.
- **Level 0**: fresh `cdk init` sample → `cdk deploy` deploys to current account/region with the
  wrapper installed but no config file (assert wrapper is inert).
- **Level 1**: add `cicd.config.ts` with 2 stages → `cdk-cicd deploy-ci` provisions the pipeline;
  push triggers per-stage deploys; assert CodeBuild project count is small and constant per stage.
- **App-config**: `config/local.json` used by `cdk deploy`; `config/dev.json` used for the `dev`
  stage synth; a missing required key fails `cdk synth` non-zero with the right `ConfigError.kind`
  (unit + integration).
- **Multi-region & forced roles**: a stage with `regions: [...]` produces one assembly per region;
  `deployment.deployRole` is threaded into the synthesizer/deploy.
- **Container mode**: Repo 1 builds & pushes the config-agnostic image; `defineDeployment` +
  `deploy --from-image` runs it against a target's config, synthing in-container then deploying.
- Update `samples/cdk-ts-example` and `cdk-python-example` to the v3 shape as living smoke tests.
