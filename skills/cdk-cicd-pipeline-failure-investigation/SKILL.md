Use it for any investigation whose title reads "Pipeline <name> failed at <stage> / <action>", or when a CodeBuild build or CloudFormation stack of such a pipeline fails. It maps each action to what it runs, where its logs and stacks live (pipeline account vs stage account), and the usual root causes, including a CDK bootstrap qualifier that does not match the configuration and context lookups that run in the pipeline because `cdk.context.json` was not committed.

# Investigating a failed cdk-cicd-wrapper pipeline

cdk-cicd-wrapper turns a `cicd.config.ts` in the application's repository into a CodePipeline. Almost every
action is a CodeBuild project running the `cdk-cicd` CLI, so the root cause is nearly always in a CodeBuild
log or in the CloudFormation events of a stack the action deployed. The pipeline lives in one account and
Region (the pipeline account). Each stage deploys into its own account and Region, which can differ.

## Step 1: Identify the failed action

From the investigation description or `codepipeline:ListActionExecutions` for the execution, take the
stage name, action name, provider and `externalExecutionUrl`/summary. Then look the action up in
[references/pipeline-layout.md](references/pipeline-layout.md) to learn what it ran and where.

Which kind of pipeline it is:

- a `Plan` stage followed by `Deploy-<n>` stages: a container-mode **Repo 2** CD pipeline;
- only `Source` and one `Deploy-<stage>` stage: a Repo 2 **auto-deploy** pipeline, started by an image push;
- a `BuildImage` stage: a container-mode **Repo 1** image build;
- otherwise `Build`, `UpdatePipeline` and one stage per environment: the main pipeline. An `Assets` stage
  and CloudFormation `Prepare`/`Deploy` actions mean the `cdk-pipelines` engine.

## Step 2: Read the evidence where it lives

- **CodeBuild actions** (`Build`, `Synth`, `SelfMutate`, `Deploy-<stage>`, the `Assets` actions, `Plan`,
  `BuildAndPush`): open the build behind the action's `externalExecutionUrl` and read its log in CloudWatch
  Logs (log group `/aws/codebuild/<project-name>` in the **pipeline** account). CodeBuild marks the failing
  command with `Command did not exit successfully` and the phase with `COMMAND_EXECUTION_ERROR`; the cause
  is in the output just above that, so read upward from it rather than from the last line.
- **Deploy actions** (`Deploy-<stage>`, CDK Pipelines `Prepare`/`Deploy`, `Await-<stage>`): the stacks are in
  the **stage** account and Region. Read `cloudformation:DescribeStackEvents` there and find the first
  `*_FAILED` event with its `ResourceStatusReason`. A stack in `UPDATE_ROLLBACK_COMPLETE` or
  `ROLLBACK_COMPLETE` was rolled back; the reason is on the first failed resource, not on the stack.
- **`Await-<stage>`** (only with `asyncDeploy`): a Lambda in the pipeline account executes the change sets
  the `Deploy-<stage>` build prepared, and fails the action with the stack status it saw. Go straight to the
  stage account's stack events.
- **Source**: the source action's error message is the evidence (repository, branch, connection status).

## Step 3: Rule out the two causes that surface far from where they start

Check both whenever the error names a `cdk-<qualifier>-…-role`, a `/cdk-bootstrap/<qualifier>/version`
parameter or a context lookup, and whenever a deploy changed or replaced resources the commit did not touch.

### The bootstrap qualifiers

A CDK bootstrap is identified by its qualifier. Its roles are `cdk-<qualifier>-<kind>-role-<account>-<region>`
(`deploy`, `file-publishing`, `image-publishing`, `lookup`, and `cfn-exec` for CloudFormation), and its
version is the SSM parameter `/cdk-bootstrap/<qualifier>/version`. The CDK guide requires synthesis to use
the qualifier the environment was bootstrapped with. A cdk-cicd pipeline can use two qualifiers. Read each
of the values below, and never assume one:

1. **The stages' qualifier.** `qualifier` in `cicd.config.ts` (in `deploy.config.ts` for a container-mode
   Repo 2). Without it, a config with `application` derives one: the application name's letters and digits,
   lowercased, first 10 characters (`cdkcicd` if none are left). Renaming `application` therefore changes
   it. A config with neither uses the pipeline stack's qualifier below. Every lookup and every
   `Deploy-<stage>` in the stage accounts uses this one.
2. **The pipeline stack's qualifier.** The CDK context `@aws-cdk/core:bootstrapQualifier`, normally set in
   `cdk.json`; without it, the CDK's default. `SelfMutate` deploys with it into the pipeline account.
3. **The qualifier in the error.** It is the segment after `cdk-` in the role ARN, or after `/cdk-bootstrap/`
   in the parameter name.

Then read what the target account and Region actually have. The bootstrap stack's name varies
(`CDKToolkit`, `CDKToolkit-<qualifier>`), so find it by its `Qualifier` parameter:

```sh
aws ssm get-parameter --name /cdk-bootstrap/<qualifier>/version --region <region> --query Parameter.Value
aws cloudformation describe-stacks --region <region> --output text --query \
  "Stacks[?Parameters[?ParameterKey=='Qualifier']].[StackName, Parameters[?ParameterKey=='Qualifier'] | [0].ParameterValue, Parameters[?ParameterKey=='TrustedAccounts'] | [0].ParameterValue, Parameters[?ParameterKey=='TrustedAccountsForLookup'] | [0].ParameterValue]"
```

- **The error's qualifier is not the one you worked out for that stack.** Check that you compared it with the
  right value (the stages' or the pipeline stack's). If you did, the app sets its own synthesizer
  (`synthesizer` or `defaultStackSynthesizer` in `bin/`); the pipeline's IAM still grants only the
  configured qualifier's roles.
- **The qualifier matches, but no bootstrap stack in that account and Region carries it.** The account was
  bootstrapped with another qualifier, or the configured one changed, most often through a renamed
  `application`. Two fixes, and the choice is the user's, so say which values you found where:
  - bootstrap the configured qualifier:
    `cdk bootstrap aws://<account>/<region> --qualifier <qualifier> --toolkit-stack-name CDKToolkit-<qualifier>`.
    Never leave out `--toolkit-stack-name`: without it the command rewrites the stack named `CDKToolkit`;
  - or set `qualifier`, and for the pipeline stack the `cdk.json` context, to the qualifier the accounts
    have. A new `qualifier` reaches the stages through `SelfMutate`. A new `cdk.json` context needs the
    manual step in the next bullet.
- **`SelfMutate` after a commit changed the pipeline stack's qualifier** (the `cdk.json` context). The running
  UpdatePipeline role holds only the roles of the qualifier from the pipeline's previous synth. `SelfMutate`
  deploys into its own account, so the CLI raises no assume error. It warns `… could not be used to assume
  '<role ARN>', but are for the right account. Proceeding anyway.`, and a later call made with the build
  role's own permissions fails. The fix: the new qualifier's bootstrap in the pipeline account and Region,
  then one `cdk-cicd deploy-ci` by hand.
- **A stage in another account** needs the pipeline account in that bootstrap's `TrustedAccounts`. Lookups
  alone can also be allowed through `TrustedAccountsForLookup`; `--trust` implies lookup trust.
- **A stack named `CDKToolkit` whose `Qualifier` other apps in that account do not expect.** Someone ran
  `cdk bootstrap --qualifier <q>` without `--toolkit-stack-name`, or ran `cdk bootstrap` in a project whose
  `cdk.json` sets the context but no `toolkitStackName`. Report it: repairing a shared bootstrap stack is the
  account owner's decision.

### Context lookups and `cdk.context.json`

Lookups read the AWS account at synth time. The CDK guide lists, for example, `Vpc.fromLookup`,
`HostedZone.fromLookup`, `StringParameter.valueFromLookup`, machine-image lookups and
`stack.availabilityZones`, and other constructs have `fromLookup` methods too. The CDK caches each result in
the project's `cdk.context.json`, under a key that names the provider, the account and the Region, for
example `vpc-provider:account=<account>:filter.isDefault=true:region=<region>:returnAsymmetricSubnets=true`.
The AWS CDK guide says to commit that file. Without it a pipeline repeats every lookup, and the results "may
suddenly be different in unexpected ways, and even produce results that cannot be deployed or will cause
data loss" (CDK Pipelines README).

Check the repository at the commit the execution ran. Is `cdk.context.json` there and not listed in
`.gitignore`? Does it hold a key for every lookup in every stage's account and Region? A developer who
added a lookup, synthesized locally and committed only the code leaves it missing. Every synth then runs
the lookups it lacks, assuming `cdk-<stages' qualifier>-lookup-role-<stage account>-<region>`:

- `Build`: for every stage under `ASSEMBLY_PROMOTION` (the default). Under `DEPLOY_TIME_SYNTH`, only for the
  stages it synthesizes, which are `ci.synthStages` or else the first stage.
- each `Deploy-<stage>` that `Build` did not synthesize (`DEPLOY_TIME_SYNTH` only);
- the `cdk-pipelines` engine's `Synth`, container mode's `BuildAndPush`, and Repo 2's deploys.

What it looks like in the CodeBuild log:

- **A stage in the pipeline's own account:** the warning `… could not be used to assume
  'arn:aws:iam::<account>:role/cdk-<qualifier>-lookup-role-<account>-<region>', but are for the right account.
  Proceeding anyway.` The lookup then runs with the build's own role. That role holds no permission for the
  lookup itself, because the wrapper relies on the lookup role for that, so an access-denied error on the
  describe call follows. The lookup role is missing (no bootstrap with that qualifier in that Region), or the
  ARN carries a qualifier the pipeline was not granted.
- **A stage in another account:** `Could not assume role in target account using current credentials (which
  are for account <pipeline account>) … cdk-<qualifier>-lookup-role-… Please make sure that this role
  exists in the account.` Either there is no bootstrap with that qualifier there, or it does not trust the
  pipeline account.
- **`Context lookups have been disabled. Make sure all necessary context is already in 'cdk.context.json' …
  Missing context keys: '…'`**: the synth ran with `--no-lookups` or `"lookups": false` in `cdk.json`, which
  the wrapper's own synth never sets. The missing keys are named.
- **No error at all, but a deploy that changes or replaces resources the commit did not touch.** Often a
  lookup returned a different value than on the developer's machine. An aws-cdk-lib upgrade or a
  feature-flag change looks the same, so compare the `cdk.context.json` keys first.

The fix: run `npx cdk-cicd synth --all` with credentials that can perform those lookups, then commit
`cdk.context.json`, which the synth writes to the project root. Do not edit the file by hand. To take a
newer value on purpose, run `cdk context --reset <key>` and synthesize again.

## Step 4: Match the usual causes

| Symptom | Likely cause | Where to confirm |
| --- | --- | --- |
| `Build` fails in `npm ci` | lockfile out of sync with package.json, or a private registry the build cannot reach | Build log; `codeArtifact`/`npmRegistry`/`proxy` in cicd.config |
| `Build` fails in `npm run audit`, `build` or `test` | the application's own checks failed; these are the project's npm scripts | Build log |
| `Build` fails in `cdk-cicd synth` with `AwsSolutions-…` | a cdk-nag rule failed on the application's stacks | Build log, the rule ID names the resource |
| `Build` fails in `cdk-cicd synth` with `… bind no AWS account` | a stack in the application's `bin/` has no `env`; the pipeline needs every stack bound to an account (for example `env: { account: process.env.CDK_DEFAULT_ACCOUNT, region: process.env.CDK_DEFAULT_REGION }`) | Build log names the stacks; the app's `bin/` |
| `Build` fails loading `cicd.config.ts` with `needs ts-node` or `ts-node could not load` | `ts-node` is missing from the project's devDependencies, or the config does not compile | Build log; `package.json`, `cicd.config.ts` |
| Repo 2 `Plan` or `Deploy-<stage>` fails with `… sets aws.accountId …` or `… sets aws.region …, but deploy.config target …` | the application's `config/<stage>.json` and the `deploy.config.ts` target disagree on the account or Region | `config/<stage>.json` in the application, the target in `deploy.config.ts` |
| `Deploy-<stage>` fails with `Could not assume role in target account …` (a stage in another account), or warns `… could not be used to assume …, but are for the right account` and then fails (the pipeline's own account) | the stage account is not bootstrapped with `--trust <pipeline account>`, or uses another qualifier | Step 3, the bootstrap qualifiers |
| `Deploy-<stage>` fails with `SSM parameter /cdk-bootstrap/<qualifier>/version not found` | the stage's account and Region have no bootstrap with that qualifier | Step 3, the bootstrap qualifiers |
| `Build` warns `… could not be used to assume '…-lookup-role-…', but are for the right account`, then fails access-denied; or `Could not assume role in target account … lookup-role …`; or `Context lookups have been disabled … Missing context keys` | `cdk.context.json` is not committed, or lacks a stage's keys, so the lookups run in the pipeline, and the stage's lookup role is missing or does not trust the pipeline account | Step 3, context lookups |
| a deploy changes or replaces resources the commit did not touch | often a lookup that returned a new value because `cdk.context.json` is not committed | Step 3, context lookups |
| `SelfMutate` warns `… could not be used to assume 'cdk-<qualifier>-…-role-…'` and then fails, after a `cdk.json` change | the pipeline stack's qualifier changed; its UpdatePipeline role holds only the previous one | Step 3, the bootstrap qualifiers |
| `Deploy-<stage>` or `Await-<stage>` fails, stack rolled back | a resource in the application's stack failed to create or update | stage account: first `*_FAILED` stack event |
| `SelfMutate` fails | the pipeline's own stack failed to update after a `cicd.config.ts` change | pipeline account: the pipeline stack's events |
| an `Assets` action fails (`cdk-pipelines`) | the asset could not be built (a Docker build error) or published: the stage account's bootstrap bucket or ECR repository is missing, or does not trust the pipeline account | build log; stage account: the bootstrap stack with that qualifier |
| `Source` fails | branch or repository missing, CodeStar connection not `AVAILABLE`, S3 object missing | source action message |
| Repo 2 `Deploy-<stage>` fails pulling the image | the image tag/digest does not exist, or a cross-account ECR policy does not allow the pipeline role | build log; the ECR repository policy |

The deployed application stacks are named by the application's own `bin/` code; a stage-qualified name
such as `<stage>-<app>` or `<app>-<stage>` is common. The pipeline stack is `<application>-pipeline` unless
`pipelineStackName` overrides it.

## Step 5: Summarize

Report, in this order:

1. The failed stage and action, and what that action runs (from the layout reference).
2. The first error, quoted from the log or stack event, with the account and Region it came from.
3. The root cause, and whether it lies in the change that started the execution, in the target environment
   (account, bootstrap, quotas, an existing resource), or in the pipeline configuration (`cicd.config.ts`).
   For a qualifier mismatch, give each qualifier and where it came from. For lookups, say whether
   `cdk.context.json` is committed and which keys are missing.
4. The fix, naming the `cicd.config.ts` field, the application code or the account setup to change. Say
   when a retry alone will do (a transient error) and when it will not.
