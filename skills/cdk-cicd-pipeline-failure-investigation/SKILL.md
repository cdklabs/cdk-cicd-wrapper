# Investigating a failed cdk-cicd-wrapper pipeline

cdk-cicd-wrapper turns a `cicd.config.ts` in the application's repository into a CodePipeline. Almost every
action is a CodeBuild project running the `cdk-cicd` CLI, so the root cause is nearly always in a CodeBuild
log or in the CloudFormation events of a stack the action deployed. The pipeline lives in one account and
Region (the pipeline account). Each stage deploys into its own account and Region, which can differ.

## Step 1: Identify the failed action

From the investigation description or `codepipeline:ListActionExecutions` for the execution, take the
stage name, action name, provider and `externalExecutionUrl`/summary. Then look the action up in
[references/pipeline-layout.md](references/pipeline-layout.md) to learn what it ran and where.

Which kind of pipeline it is:

- a `Plan` stage followed by `Deploy-<n>` stages: a container-mode **Repo 2** CD pipeline;
- only `Source` and one `Deploy-<stage>` stage: a Repo 2 **auto-deploy** pipeline, started by an image push;
- a `BuildImage` stage: a container-mode **Repo 1** image build;
- otherwise `Build`, `UpdatePipeline` and one stage per environment: the main pipeline. An `Assets` stage
  and CloudFormation `Prepare`/`Deploy` actions mean the `cdk-pipelines` engine.

## Step 2: Read the evidence where it lives

- **CodeBuild actions** (`Build`, `Synth`, `SelfMutate`, `Deploy-<stage>`, the `Assets` actions, `Plan`,
  `BuildAndPush`): open the build behind the action's `externalExecutionUrl` and read its log in CloudWatch
  Logs (log group `/aws/codebuild/<project-name>` in the **pipeline** account). CodeBuild marks the failing
  command with `Command did not exit successfully` and the phase with `COMMAND_EXECUTION_ERROR`; the cause
  is in the output just above that, so read upward from it rather than from the last line.
- **Deploy actions** (`Deploy-<stage>`, CDK Pipelines `Prepare`/`Deploy`, `Await-<stage>`): the stacks are in
  the **stage** account and Region. Read `cloudformation:DescribeStackEvents` there and find the first
  `*_FAILED` event with its `ResourceStatusReason`. A stack in `UPDATE_ROLLBACK_COMPLETE` or
  `ROLLBACK_COMPLETE` was rolled back; the reason is on the first failed resource, not on the stack.
- **`Await-<stage>`** (only with `asyncDeploy`): a Lambda in the pipeline account executes the change sets
  the `Deploy-<stage>` build prepared, and fails the action with the stack status it saw. Go straight to the
  stage account's stack events.
- **Source**: the source action's error message is the evidence (repository, branch, connection status).

## Step 3: Match the usual causes

| Symptom | Likely cause | Where to confirm |
| --- | --- | --- |
| `Build` fails in `npm ci` | lockfile out of sync with package.json, or a private registry the build cannot reach | Build log; `codeArtifact`/`npmRegistry`/`proxy` in cicd.config |
| `Build` fails in `npm run audit`, `build` or `test` | the application's own checks failed; these are the project's npm scripts | Build log |
| `Build` fails in `cdk-cicd synth` with `AwsSolutions-…` | a cdk-nag rule failed on the application's stacks | Build log, the rule ID names the resource |
| `Deploy-<stage>` fails with `AccessDenied` on `sts:AssumeRole`, or `Need to perform AWS calls for account …, but the current credentials are for …` | the stage account is not bootstrapped with `--trust <pipeline account>`, or uses another qualifier | stage account: `CDKToolkit` stack, `qualifier` in cicd.config |
| `Deploy-<stage>` fails with `SSM parameter /cdk-bootstrap/<qualifier>/version not found` | the stage account/Region is not bootstrapped with that qualifier | stage account, that Region |
| `Deploy-<stage>` or `Await-<stage>` fails, stack rolled back | a resource in the application's stack failed to create or update | stage account: first `*_FAILED` stack event |
| `SelfMutate` fails | the pipeline's own stack failed to update after a `cicd.config.ts` change | pipeline account: the pipeline stack's events |
| an `Assets` action fails (`cdk-pipelines`) | the asset could not be built (a Docker build error) or published: the stage account's bootstrap bucket or ECR repository is missing, or does not trust the pipeline account | build log; stage account: `CDKToolkit` stack |
| `Source` fails | branch or repository missing, CodeStar connection not `AVAILABLE`, S3 object missing | source action message |
| Repo 2 `Deploy-<stage>` fails pulling the image | the image tag/digest does not exist, or a cross-account ECR policy does not allow the pipeline role | build log; the ECR repository policy |

The deployed application stacks are named by the application's own `bin/` code; a stage-qualified name
such as `<stage>-<app>` or `<app>-<stage>` is common. The pipeline stack is `<application>-pipeline` unless
`pipelineStackName` overrides it.

## Step 4: Summarize

Report, in this order:

1. The failed stage and action, and what that action runs (from the layout reference).
2. The first error, quoted from the log or stack event, with the account and Region it came from.
3. The root cause, and whether it lies in the change that started the execution, in the target environment
   (account, bootstrap, quotas, an existing resource), or in the pipeline configuration (`cicd.config.ts`).
4. The fix, naming the `cicd.config.ts` field, the application code or the account setup to change. Say
   when a retry alone will do (a transient error) and when it will not.
